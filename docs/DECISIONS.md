# Decisions

Every deviation from the specification, and every choice the specification left open, is recorded here.

## D-001: Project name is Wasmward

- **Date:** 2026-10-07
- **Decision:** The project is named Wasmward, replacing the spec's placeholder name "Contract Version Guard" and the package scope `@versionguard`.
- **Why:** `versionguard` and `version-guard` are already used on npm by unrelated SemVer-enforcement packages, and the name suggests SemVer rather than code identity. Wasmward says what is watched (Wasm) and what it does (stands guard).
- **Mapping:**
  - Package: `@wasmward/core` (library and CLI).
  - CLI binary: `wasmward`.
  - Config file: `wasmward.json`.
- **Open item:** On 2026-10-07 `wasmward`, `wasm-ward` and `@wasmward/core` returned 404 on the npm registry. That proves the package names are unused. It does not reserve the `@wasmward` scope. The scope must be claimed by creating an npm organization before the first publish.

## D-002: Duplicate check (spec Phase 0, step 1)

- **Date:** 2026-10-07
- **Result:** No existing package covers spec section 2.3. Decision: build.
- **npm queries:** `soroban wasm hash`, `soroban version guard`, `soroban upgrade`, `stellar contract upgrade guard`, `soroban contract hash`, `versionguard`.
  - Nothing gates writes on Soroban Wasm hashes.
  - `soroban-guard` exists, but it is SEP-41 token conformance testing.
  - `soroban-events` and `sac-sdk` are unrelated.
  - Several `versionguard` packages exist; all are SemVer or CalVer tooling.
- **GitHub:** The only related repository is `ShippedLabs/soroban-upgrade-safeguard`. It compares Wasm builds before deployment and has no runtime component. The GitHub searches `soroban wasm hash` and `stellar contract version guard` returned no repositories.
- **Limit of the check:** GitHub code search is weak. A manual pass on GitHub and the Stellar community channels is still advisable before announcing.

## D-003: Wasm hash is the only supported-version source

- **Date:** 2026-10-07
- **Decision:** Supported versions are exact Wasm hashes listed in `wasmward.json`. Wasmward does not read the `soroban-upgrade-safeguard` interface lockfile (spec section 2.4).
- **Why:** The lockfile pins an interface hash, not code. The on-chain instance entry exposes only the Wasm hash, so using the lockfile would require downloading the live Wasm and recomputing an interface hash on every check. That is heavy in a browser and makes the fail-closed rule harder to prove.
- **Possible later work:** An optional importer that fills a hash list from a lockfile and Wasm file. Not part of the core.

## D-004: Repository layout across three repositories

- **Date:** 2026-10-07
- **Decision:** The spec describes one repository. The project owner created three, so the work maps as follows:
  - `Wasmward-backend`: the TypeScript SDK and CLI (`@wasmward/core`), everything under spec section 4 except `fixtures/`.
  - `Wasmward-contract`: the Rust upgradeable fixture contract (v1 and v2) and the deploy and upgrade scripts (spec `fixtures/contract` and `fixtures/scripts`).
  - `Wasmward-frontend`: not used in the MVP. The spec forbids UI screens and a React package (sections 1.1 and 2.4). The browser example is a seed-backlog item.
- **Consequence:** The testnet integration test lives in `Wasmward-backend` and reads `fixtures/testnet.json`. That file is produced by the `Wasmward-contract` deploy script and is git-ignored.

## D-005: TypeScript is pinned to 6.0.3, not 7.x

- **Date:** 2026-10-07
- **Decision:** `typescript` is pinned to `6.0.3`. The newest release at resolution time was `7.0.2`.
- **Why:** With 7.0.2, `typescript-eslint` refuses to run ("does not support TS 7.0") and tsup's declaration build cannot load the TypeScript JS API. Phase 0 requires lint and build to pass.
- **Follow-up:** Revisit when `typescript-eslint` and `tsup` support TypeScript 7.
- **Related:** tsup injects the deprecated `baseUrl` option into its declaration build, which TypeScript 6 rejects. `tsup.config.ts` sets `ignoreDeprecations: "6.0"` for the declaration build only.

## D-006: Stellar SDK 17 API mapping (spec section 3)

- **Date:** 2026-10-07
- **Pinned:** `@stellar/stellar-sdk` 17.2.1. Each item below was checked against the installed type definitions and a runtime probe.
- **Confirmed as specified:**
  - `rpc.Server#getLedgerEntries`, `#getNetwork` (returns `{ passphrase, protocolVersion, friendbotUrl? }`), `#getLatestLedger` (returns `{ sequence, ... }`).
  - `xdr.LedgerKey.contractData`, `xdr.LedgerKeyContractData` (constructor takes `{ contract, key, durability }`).
  - `xdr.ScVal.scvLedgerKeyContractInstance()`, `Address#toScAddress()`, `StrKey.isValidContract()`.
- **Differs from the spec text:**
  1. `getLedgerEntries` takes variadic keys: `getLedgerEntries(...keys)`. Batching spreads each chunk.
  2. `xdr.ContractDataDurability.persistent` is a static property, not a method call.
  3. Decoding uses properties and a `type` discriminant, not method chains. The spec's `entry.val.contractData().val().instance().executable()` becomes `entry.val.contractData.val.instance.executable`, after checking `entry.val.type === 'contractData'`, `.val.type === 'scvContractInstance'`, and then the executable's `type`.
  4. Wasm hash bytes come from `executable.wasmHash.toBytes()` and are hex-encoded locally.
  5. Entry keys are matched with `XdrValue#equals`, or by comparing base64 key XDR.
- **New variant:** `ContractExecutable` has three variants in v17: `contractExecutableWasm`, `contractExecutableStellarAsset` and `contractExecutableExternalRef`. The spec's `LiveExecutable` has no case for the third. Decision: map `contractExecutableExternalRef` to `{ kind: 'error' }` with a clear message, so the contract can never be reported `supported`. This follows the fail-closed rule.

## D-007: Config schema choices the spec left open

- **Date:** 2026-10-07
- **Unknown keys are rejected.** Every object in the config is strict. A typo such as `pollIntervalMS` would otherwise be ignored silently and the default used, which is the wrong failure mode for a guard.
- **`label` is optional.** The spec requires labels to be non-empty strings of at most 64 characters when present, and `ContractState.matchedLabel` is optional, so a version may have only a hash.
- **Integer intervals.** `pollIntervalMs` and `maxStalenessMs` must be integers.
- **Browser-safe split.** `loadConfig` is exported from the main entry. `loadConfigFile` lives in `src/node.ts`, published as `@wasmward/core/node`, so browser bundles never import `fs`. `src/node.ts` is not in the spec's file list; it is the file behind the export path the spec requires.
- **Byte order mark.** `loadConfigFile` strips a leading UTF-8 byte order mark before parsing, because Windows editors and PowerShell commonly write one and `JSON.parse` rejects it.
- **Dependent rules wait for independent ones.** zod skips a cross-field rule (duplicate hashes, `maxStalenessMs` against `pollIntervalMs`) while the fields it compares are themselves invalid. A user with several mistakes may therefore see them over two runs. Each run still lists every issue it can evaluate.
- **Contract-name errors.** zod 4 reports a bad record key as a generic "Invalid key in record". `loadConfig` rewrites that issue to `contract name must match <regex>`.

## D-008: Live executable lookup choices

- **Date:** 2026-10-07
- **Key limit:** The Stellar RPC docs state a maximum of 200 keys per `getLedgerEntries` request. `MAX_KEYS_PER_REQUEST` is 200. Larger sets are split into chunks that run in parallel. A failing chunk marks only its own contracts as `error`.
- **Narrow server type:** `fetchExecutables` takes `LedgerEntriesSource` (just `getLedgerEntries(...keys)`) instead of the whole `rpc.Server`. `rpc.Server` satisfies it, and tests can pass a stub.
- **Absent keys mean missing.** The docs do not say what happens for keys that do not exist. Entries for them are not returned, and Wasmward reports `missing`.
- **Archived instances may look missing.** The spec marks an instance `archived` when `liveUntilLedgerSeq < latestLedger`. A live-state RPC may omit expired entries entirely, in which case the contract is reported `missing`. Both statuses block writes, so the outcome is safe either way. Only the label differs.
- **No TTL, no trust.** A Wasm instance returned without `liveUntilLedgerSeq` is reported as `error`, because archival cannot be ruled out. A Stellar Asset Contract without a TTL is still `stellar-asset`, since that status never allows writes anyway.
- **Invalid contract IDs.** An ID that cannot be turned into a key yields `error` for that contract only. The rest of the batch is still looked up.
- **Duplicates.** A contract ID passed twice is requested once. If the RPC returns the same key twice, the first entry wins. Entries for keys that were not requested are ignored.
- **Error text.** The RPC client rejects with plain `{ code, message }` objects for JSON-RPC errors. `messageOf` reads the `message` field so errors are readable rather than `[object Object]`. A replay test found this.
- **Replay tests.** Wire-format responses are generated with the SDK's own XDR builders and served over local HTTP, so the real `rpc.Server` parsing is exercised. Responses recorded from testnet are added in Phase 7.

## D-009: Status model choices

- **Date:** 2026-10-07
- **One function decides writability.** `effectiveStatus(state, now, maxStalenessMs)` returns the status as it stands at call time: a stored `supported` becomes `stale` once the last successful lookup is older than `maxStalenessMs`, with no poller involved. `isWritable` is defined as `effectiveStatus(...) === 'supported'`, so `supported` is the only status that can ever be writable and the call-time staleness check cannot be bypassed.
- **Boundary.** Age equal to `maxStalenessMs` is still fresh ("within" the limit); one millisecond more is stale. This matches the spec's "older than".
- **Clock moving backwards fails closed.** If `now` is earlier than `lastSuccessAt`, or `now` is not a number, freshness cannot be shown, so the contract is reported `stale` and writes are blocked. The next successful poll sets a new `lastSuccessAt` and recovers. A step backwards is rare; being briefly blocked is the safe side of that trade.
- **A `supported` state with no recorded success reads as `pending`.** It cannot arise through `nextState`, but the function does not trust it.
- **Errors after a success follow the spec literally.** Once the last success is older than the limit, the status becomes `stale` whatever it was, including `unsupported` or `missing`. The last seen hash is kept for diagnosis. All of these block writes.
- **`initialState`.** The spec names `ContractState` but not how one starts. `initialState(name, contract)` creates the `pending` state with no history.
- **Results that clear fields.** A successful non-Wasm result (`stellar-asset`, `missing`, `archived`) clears `liveWasmHash` and `matchedLabel`, since no Wasm hash was observed. An unsupported hash keeps `liveWasmHash` and clears `matchedLabel`.

## D-010: Poller choices

- **Date:** 2026-10-07
- **The optional `getLatestLedger` shortcut is not implemented.** The spec allows skipping the entries call when the ledger sequence is unchanged, but only "if tests show it is correct for staleness". It is not: an RPC node that is stuck on one ledger would keep returning the same sequence, the shortcut would keep refreshing `lastSuccessAt`, and a contract would stay `supported` while the guard learns nothing. Every tick therefore does the full lookup.
- **Scheduling is a `setTimeout` chain that arms the next timer after the current tick finishes.** Two ticks cannot overlap, and a tick that outlasts the interval simply delays the next one (the lookup itself is bounded by its timeout). A stop followed by a start while an old tick is still running waits for that tick, so concurrency stays at one. This replaces the spec's "skip that fire" wording with a structure that makes the skip unnecessary.
- **The poller only schedules.** It takes a `tick()` function that returns true when every contract's lookup failed. The guard (Phase 5) supplies the tick that fetches, applies `nextState` and fires change callbacks. A tick that rejects counts as a failing tick.
- **Backoff and jitter.** The wait is `intervalMs` doubled per consecutive failing tick, capped at `maxStalenessMs / 2`, with 0 to 10 percent jitter added on top of the capped value. The real wait can therefore reach 1.1 times the cap. Writes are blocked by the call-time staleness check regardless of when the next tick runs, so this timing only affects how soon state and subscribers update.
- **Restart.** `start()` after `stop()` begins a fresh schedule with the failure count reset. A second `start()` while running returns the same promise and does nothing.

## D-011: Guard and health choices

- **Date:** 2026-10-07
- **The config is validated again** inside `createVersionGuard`. `loadConfig` is idempotent on its own output, so a hand-built or edited object cannot bypass the schema rules.
- **Narrow server type.** `createVersionGuard` takes a `GuardServer` (`getNetwork` and `getLedgerEntries`) rather than the whole `rpc.Server`, so tests can pass a fake chain. `rpc.Server` satisfies it. With no server given, the guard builds one and allows plain http only when the config URL is http, which the config schema already limits to localhost.
- **Start and the network check.** A passphrase mismatch throws `ConfigError` and starts nothing (spec). If the network cannot be reached at all, the spec is silent; `start()` rejects with an `Error` (the original is its `cause`) and starts nothing, because contracts cannot be called `supported` on an unverified network. A failed start can simply be retried. `start()` is idempotent while in flight, `stop()` cancels a start that is still verifying the network, and a restart does not repeat a verification that succeeded.
- **Nothing is writable before the network is verified.** `isWritable`, `assertWritable` and `assertWritableFresh` all require a completed `start()`.
- **Lookup timeout.** The spec gives none. A lookup waits `min(pollIntervalMs, 10s)`, so a hung request can never outlast the polling interval.
- **Freshness is dated from when the lookup began**, not when it ended, so a slow response never looks fresher than it is. Errors are judged against the current time so staleness is noticed as soon as it is real.
- **An older lookup cannot overwrite a newer one.** If a slow poll finishes after a fresh check has already seen an upgrade, the late result is dropped. Otherwise a stale `supported` could replace the correct `unsupported` until the next poll. This is tested.
- **`assertWritableFresh` fails closed.** The spec says it "runs one immediate lookup, then asserts". If that lookup errors, the stored state may still be fresh and supported; asserting on it would defeat the purpose, so the call throws `WriteBlockedError` with the lookup error in the reason.
- **Subscribers see transitions of the effective status.** Each contract remembers the last status it announced, so a change is reported once. Becoming `stale` through time alone, with no check completing, is not pushed; `status()`, `isWritable()` and `health()` still report it.
- **Listener errors are swallowed silently**, as the spec requires ("caught and do not stop the poller"). There is no error hook; adding one would be an option the spec does not list.
- **`status()` applies staleness to the status** and returns copies, so a stopped poller shows `stale` and callers cannot mutate guard state.
- **Health output.** `HealthReport` adds `network.verified`, and `ok` requires it. The RPC URL is omitted because providers often embed API keys in it and health endpoints are commonly exposed. Report fields with no value are left out rather than set to `undefined`, so the output is plain JSON.
- **Wrapper details.** `guard.guard` always returns a promise, so a block surfaces as a rejection. Unknown names throw `ConfigError` when the wrapper is created. It uses local functions rather than `this`, so it works when detached from the guard object.
- **Contract lookup uses a `Map`** so names such as `constructor` are never matched through object inheritance. Tests cover `constructor`, `toString` and `__proto__`.
- **`WriteBlockedError` message** prints the full 64-character hash, not a shortened one, so it can be pasted into the config.

## D-012: CLI choices

- **Date:** 2026-10-07
- **Two files instead of one.** The spec lists `src/cli.ts`. The logic lives in `src/cli-core.ts` as `main(argv, io)`, which returns an exit code and never calls `process.exit`. `src/cli.ts` is a four-line entry that wires it to the real stdout, stderr and exit code. This lets almost all of the CLI be tested in-process and measured by coverage, while `test/cli` still runs the built `dist/cli.js` as a separate process, as the spec's test matrix asks.
- **The Stellar SDK loads lazily.** Importing it takes several seconds on a slow disk (4 to 5 seconds here, inside a OneDrive folder). `wasmward hash` does not need it, so `config`, `node`, `fetch` and the SDK client are imported dynamically by `add` and `check` only. `hash` now starts in about 0.5 seconds. The build therefore emits a few shared chunk files next to `dist/cli.js`; `files: ["dist"]` ships them.
- **`add` needs `--label`.** The spec's command table shows `--label` unbracketed and `--config` bracketed, so the label is required even though the config schema allows a version without one.
- **`add` only extends existing contracts.** It has no way to learn a contract ID, so an unknown contract name is an error (exit 2) that lists the configured names.
- **`add` edits the file's own JSON, not the loaded config.** The loaded config has defaults filled in and hashes lowercased; writing that back would rewrite the user's file. Instead the raw document is validated, the new entry is appended, the result is validated again, and only then is it written. The output is JSON with two-space indentation and a trailing newline, keeping the file's original key order.
- **Duplicates are compared in lowercase**, so an uppercase hash already in the file counts. A duplicate is exit 2 ("invalid input") and the file is not touched.
- **Atomic write.** The new content goes to a uniquely named temporary file in the same folder, then `rename` replaces the target. If anything fails, the temporary file is removed and the original is untouched. Tests prove the target still holds the old content at the moment of the rename.
- **`check` exit codes.** The spec gives 0 (all supported), 1 (any not supported) and 2 (config or network error). A lookup that errors for a contract means its live code could not be determined at all, so that is reported as 2, not 1, and takes precedence over 1 when both occur. Every contract's status is still printed.
- **`check` verifies the network first.** It calls `getNetwork` and compares the passphrase before looking anything up; a mismatch or an unreachable RPC is exit 2. Both calls use a timeout of the smaller of the poll interval and 10 seconds.
- **`--json` everywhere.** Success output is JSON. For `check` it is the same shape as `guard.health()` plus `exitCode`. With `--json`, errors are printed as `{ "ok": false, "error", "exitCode" }` on stdout instead of text on stderr, so a pipeline gets parseable output on every path.
- **`--help` / `-h`** prints usage on stdout and exits 0. This is not in the spec; it costs a few lines and a command-line tool without it is hard to use. With no command, usage goes to stderr and the exit code is 2.

## D-013: Fixture and testnet integration choices

- **Date:** 2026-10-07
- **The fixture lives in `Wasmward-contract`** (D-004). Its `scripts/deploy.sh` writes `testnet.json` and `build/`, both git-ignored. The integration test in this repository reads them from `../Wasmward-contract`, or from `WASMWARD_FIXTURE_DIR`.
- **Constructor.** The fixture uses `__constructor(admin)`, which the pinned `soroban-sdk` 26.1.1 supports, rather than a separate `init()`.
- **`soroban-sdk` is 26.1.1, not the newest (28.0.0).** It is the version the Stellar CLI 27 `contract init` template pins. Testnet reports protocol 29, and contracts built with an older SDK keep running on a newer protocol; the deploy and upgrade on testnet confirm it.
- **Secrets.** `deploy.sh` uses `FIXTURE_SECRET` when it is set in the environment or in `.env`. Otherwise it generates a fresh identity in a temporary directory and appends only the secret to `.env`; nothing is printed. The Stellar CLI's own copy of the identity lives in `.stellar-keys/` (not `.stellar/`, which the CLI treats as a legacy config folder and warns about). `testnet.json` contains public values only. `.env`, `.stellar-keys/`, `testnet.json` and `build/` are git-ignored.
- **Hash check in two places.** `deploy.sh` fails if a locally computed SHA-256 differs from the hash Stellar returns on upload. The integration test then recomputes both hashes with `hashWasm` and compares them with `testnet.json`, so the library's own hash function is tested against the chain.
- **The upgrade is signed with the SDK, not the CLI.** The test builds, simulates, signs and sends the `upgrade` transaction itself from `FIXTURE_SECRET`, so it needs no Stellar CLI on the machine that runs it.
- **Re-runnable.** The test restores the contract to v1 before it starts, if an earlier run left it on v2, and again when it finishes, so one deployed fixture can be tested repeatedly.
- **Detection time is measured on the local clock.** The test starts counting when the upgrade is confirmed. An earlier version compared the ledger close time with the local clock and reported 23 seconds for a test that ran in 6; the local clock here runs well ahead of ledger time, so that number was an artifact, and the approach was dropped.
- **Skipped, not failed, without a fixture.** With no `testnet.json` or secret, the integration tests skip and print why. They never pass by default: the CI job deploys the fixture first.
- **CI.** The `integration` job checks out `Wasmward-contract`, installs the Stellar CLI release binary, runs `deploy.sh`, then the tests. It always runs on manual dispatch and on pushes to main only when a `FIXTURE_SECRET` repository secret exists (without it, `deploy.sh` would ask friendbot to fund a new account on every push). The Linux CLI download path has not yet been run on a hosted runner.
- **Recorded responses.** `test/fixtures/recorded/testnet-v1.json` holds the real `getLedgerEntries` and `getNetwork` replies for the deployed fixture. `test/replay/recorded.test.ts` serves them over HTTP to the real `rpc.Server`.

## D-014: Release preparation choices

- **Date:** 2026-10-07
- **Version 0.1.0 is prepared, not published, not tagged.** `package.json` is at 0.1.0 with repository, bugs, homepage, keywords and `publishConfig` (public, with provenance). Publishing needs two things that only the project owner can provide: the `@wasmward` scope claimed on npm (D-001) and an `NPM_TOKEN` repository secret. `.github/workflows/release.yml` publishes with provenance when a `v*` tag is pushed, after lint, typecheck, build and the coverage gate, and it refuses a tag that does not match the package version. Nothing publishes until a tag is pushed.
- **The changelog entry is dated "Unreleased".** The date is set when the version is tagged.
- **README example.** It targets the Wasmward test contract on testnet, so it runs as written with no setup. If that contract expires, the example prints why writes are blocked rather than failing. `test/integration/readme.test.ts` extracts the first `js` block from the README and runs it, so the example cannot drift from the code.
- **Browser bundle check.** `test/unit/browser-bundle.test.ts` builds the main entry with tsup for `platform: browser` with every dependency inlined, then lists the Node built-ins the output still imports; the list must be empty. The bundler keeps built-ins as external imports instead of failing, which is why the output is inspected. Two controls prove the check can fail: the Node-only entry does import `fs/promises`, and the helper recognises each import spelling.
- **Package contents.** `files: ["dist"]` plus npm's automatic README, LICENSE and package.json. A test runs `npm pack --dry-run` and fails on any other file. The CLI's lazy chunks and source maps are inside `dist`.
- **`npx` from the tarball.** The CI test job packs the package and runs `npx --package ./wasmward-core-*.tgz wasmward hash README.md` and `--help` on Node 20 and 22. Locally the same tarball was extracted and run with the installed dependencies linked, including a command that loads the lazy chunks; a real `npx` install was not run locally because the npm registry is too slow on this machine.
- **Security policy.** It names GitHub Security Advisories as the private channel and lists which reports matter most, but gives no response-time promise; that is a commitment for the maintainers to make.
- **The seed backlog is not opened.** The spec lists five issues to open after the MVP. Opening them publishes content on a public repository, so it waits for the project owner's go-ahead.

## D-015: `wasmward watch` (seed-backlog item, built on request)

- **Date:** 2026-10-08
- **Built although the spec lists it as a later backlog item.** The spec says not to implement the seed backlog "as part of this build". The project owner asked for more of the project to be built, and this was the smallest self-contained item, so it was added as part of 0.1.0. The other four backlog items are still not built, and none of the issues has been opened.
- **It is the guard, printed.** `watch` runs `createVersionGuard` with the config, so it verifies the network passphrase first and uses the same status model, poller and block reasons as an application would. It adds no checking logic of its own.
- **What is printed.** One line per status change with an ISO timestamp, the contract name, the transition, and either the live hash and label or the reason it is blocked. A contract whose first lookup failed never changes status, so it is reported once as `pending -> pending` with the error. `Watching N contract(s)` and the Ctrl+C hint go to stderr, so stdout holds only changes. With `--json` each line is one JSON object (`time`, `contract`, `from`, `to`, and `liveWasmHash`, `matchedLabel` or `reason` when they apply) and nothing is written to stderr.
- **Stopping.** The entry point aborts an `AbortController` on SIGINT or SIGTERM. `main` takes it as `io.signal`, stops the guard (waiting for a check in progress), and exits 0. Calling `watch` without a signal is an internal error rather than an endless loop.
- **Exit codes.** 0 after Ctrl+C. 2 if it cannot start: bad config, wrong network, or an unreachable RPC (the same rules as `check`). It does not exit non-zero because a contract became unsupported; that is what it is there to show.
- **Lazy loading.** The guard module is imported only by `watch`, so `hash` stays fast (D-012).

## D-016: Pairing guide with soroban-upgrade-safeguard (seed-backlog item, built on request)

- **Date:** 2026-10-08
- **Built although the spec lists it as a later backlog item**, at the project owner's request, as `docs/PAIRING.md`. Three of the five backlog items are now built or in progress: `watch` (D-015) and this guide. The browser example, multi-network config and alternate-RPC retry remain, and no backlog issue has been opened.
- **Division of labour.** safeguard compares builds before an upgrade and answers "is it safe for callers?". Wasmward answers "does this app support the code that is live?" and enforces it at runtime. The guide orders them: hash the candidate, read the live hash, run safeguard with that hash as `--expected-wasm-hash` so its RPC baseline is pinned, then `wasmward add`, then `check` before and after the contract upgrade.
- **Still no dependency on safeguard's formats** (D-003). The two tools meet at a Wasm hash and a process exit code.
- **What was verified.** Every `wasmward` command in the guide was run against the live testnet fixture. The `jq` extraction was tested with an equivalent Node one-liner because `jq` is not installed on this machine, and under `bash -e -o pipefail`, which GitHub Actions uses: the first draft of the snippet failed there whenever the config did not yet support the live code, so the guide now reads the output with `|| true` and stops with a message if no live hash was returned.
- **What was not verified.** The safeguard commands come from its README. Its repository could not be built at the time of writing: `cargo install --git` on the default branch fails with a compile error in `src/logging.rs` (a helper function declared inside `impl FromStr`), and after patching that one, a second error in the binary (struct literals missing fields). The guide says plainly which parts were run, and tells readers to check safeguard's README for current flags. The failure has not been reported upstream; opening an issue on someone else's repository is left to the project owner.
- **Not a template for every contract.** The upgrade and build steps in the GitHub Actions sketch are placeholders (`./scripts/build-contract.sh`, `./scripts/upgrade-contract.sh`) that the reader replaces.

## D-017: Browser example (seed-backlog item, built on request)

- **Date:** 2026-10-08
- **Built although the spec lists it as a later backlog item**, at the project owner's request. It lives in `Wasmward-frontend`, the third repository, which had no other planned content (D-004). The spec still forbids a React package and UI screens inside `@wasmward/core`; this is a standalone example page that uses the library, not part of it. With `watch` (D-015) and the pairing guide (D-016), three of the five backlog items are now done. Multi-network config and alternate-RPC retry remain; no backlog issue has been opened.
- **No framework, one dependency.** The page is `index.html` plus `src/main.js`, bundled with esbuild (pinned to 0.27.7, the version already in the pnpm store). A dependency-free Node server (`serve.mjs`) serves it locally.
- **The library is read from a sibling checkout.** `@wasmward/core` is not published, so `build.mjs` aliases it to `../Wasmward-backend/src/index.ts` (or `WASMWARD_CORE_DIR`). The backend's own dependencies resolve from that checkout. When the package is published the alias becomes an ordinary dependency. The CI workflow checks out both repositories to build.
- **It shows the failure, not just the happy path.** A switch makes the page pretend to be an older release that never listed the contract's current hash, so a visitor sees the status turn `unsupported`, the button turn off, and the exact `WriteBlockedError` text, without needing the contract to be upgraded.
- **Safe rendering.** Everything from the guard or RPC is set with `textContent`; no HTML is built from it.
- **Verified in a real browser** (the built-in browser pane), against live testnet: the RPC allows cross-origin requests from a page; the status reached `supported` with the correct hash; the button worked when supported and was disabled with the right message after switching; no console errors. A screenshot at phone width found one flaw, a long hash overflowing its container, which was fixed and re-checked. The frontend CI job builds it from a clean checkout on a hosted runner.
- **What is not tested automatically.** There is no automated browser test; the checks above were interactive. The CI job proves it builds and that the bundle has no Node-only imports.

## D-018: Fallback RPC endpoints (seed-backlog item, built on request)

- **Date:** 2026-10-08
- **Built although the spec lists it as a later backlog item** ("if users request it"), at the project owner's request. With `watch`, the pairing guide and the browser example, four of the five backlog items are done. Only multi-network config remains, and no backlog issue has been opened.
- **Why it earns its place.** With one RPC, an outage longer than `maxStalenessMs` blocks every write, including to contracts that did not change. A spare endpoint turns that into a non-event, and the guard stays fail-closed throughout.
- **Config.** `network.fallbackRpcUrls`, optional, at most 4 (`MAX_FALLBACK_RPC_URLS`; more only slows a failing lookup), each under the same https-or-localhost rule. A fallback may not repeat the primary or another fallback; URLs are compared ignoring host case, a default port and a trailing slash. The loaded config always has the array (empty by default). Because that makes it a required output field, `createVersionGuard` now takes a `WasmwardConfigInput` where it is optional; `WasmwardConfig` is unchanged for anyone who only reads a config.
- **All the logic is in `src/endpoints.ts`** (`createEndpointSet`), shared by the guard and `wasmward check`; `watch` uses the guard. With one server it behaves exactly like before: all 369 earlier tests passed unchanged apart from two shape assertions.
- **Failover trigger.** A lookup fails over only when it produced no usable answer for any contract. An answer of any kind, including `missing`, `archived` and `stellar-asset`, is not a failure, and an error affecting only some contracts does not make the guard ask another endpoint.
- **Fail-closed network rule.** No endpoint is used for lookups before it has reported the configured passphrase. A fallback that reports another network is rejected permanently, never looked up, and never trusted. A *primary* that reports another network is a `ConfigError` at start (as the spec says), and fallbacks are not consulted to override it. A fallback that is on the wrong network while the primary is down leaves the contract `stale`/blocked, which tests cover.
- **Start.** If the primary cannot be reached, each fallback is tried in turn; if none can, `start()` rejects with `Could not verify the network: ...`, naming endpoints by position. (The single-endpoint message is unchanged. The `cause` property of that error is no longer set.)
- **Preference.** The guard stays on a working fallback instead of waiting out the primary's timeout every poll, and tries the primary first again on every 6th lookup (`PRIMARY_RETRY_EVERY`), so it returns to the primary on its own.
- **Timing.** Each attempt keeps the usual timeout (the smaller of the poll interval and 10 s), one after another, so a lookup in which every endpoint hangs takes up to that times the number of endpoints. Freshness is still dated from when the lookup started, so a slow failover cannot make data look fresher than it is, and call-time staleness still blocks writes regardless.
- **Privacy.** Endpoints are named by position, not URL, in errors and the health report, since RPC URLs often carry API keys. `health().network.usingFallback` is a boolean for alerting. Text from the underlying client error is passed through as given.
- **What this does not do.** It does not compare endpoints with each other, so every listed endpoint is trusted as much as a lone one; an RPC that lies can still make an unsupported contract look supported. There is no parallel or hedged querying. There is no per-endpoint health detail beyond `usingFallback`.
- **Verification.** 60 new tests: 27 on the failover logic (including hanging endpoints with fake timers), 31 across config rules, the guard and `check`, and 2 that run the built binary with real HTTP clients against a dead primary port and a local fake RPC. The same was run by hand against live testnet: `wasmward check` with a dead primary and the real testnet RPC as fallback exited 0 with `usingFallback: true`; with both dead it exited 2. While writing the CLI tests, a fixture bug (a different contract ID in the config than on the fake chain) made two tests pass or fail for the wrong reason; it was caught because one expected success failed, and fixed.

## D-019: Several networks in one config file (seed-backlog item, built on request)

- **Date:** 2026-10-08
- **Built although the spec lists it as a later backlog item**, at the project owner's request. This was the last of the five seed-backlog items, so all five are now done. None of the backlog issues has been opened.
- **Format.** An optional `networks` section. Each entry is a complete single-network config without `version`, so moving to it is a matter of wrapping what you already have, and every existing rule (hash format, staleness limits, fallback endpoints and so on) applies unchanged inside each network. Network names follow the contract-name rule. The two shapes cannot be mixed. A file without `networks` behaves exactly as before.
- **Alternatives rejected.** A `network` field on each contract (every consumer of `WasmwardConfig` would have to cope with several RPCs and passphrases at once, which touches the guard, health report and CLI) and several top-level documents. Keeping one network per `WasmwardConfig` leaves the guard, endpoints, poller and health report untouched: choosing a network happens at load time, and the guard sees an ordinary config.
- **Choosing is explicit and never defaulted.** `loadConfig(input, { network })` throws for a multi-network file without a name, listing the names. It also throws if a name is given for a single-network file. Silently picking a network, or silently ignoring a requested one, could aim a write at mainnet when testnet was meant. The one convenience: the CLI's `add` and `watch` use the network automatically when the file has exactly one.
- **Where the choice is not needed.** `loadConfigDocument` returns every network, and `wasmward check` without `--network` checks them all, because a deploy gate should cover everything in the file. A failure on one network is reported and does not stop the others. The exit code is the highest of the networks (2 outranks 1 outranks 0), consistent with D-012.
- **Errors.** All networks are validated together and their problems listed in one error with full paths (`$.networks.mainnet.contracts.vault.contractId`). A bad key in a record is reported as a "network name" or "contract name" error according to which record it is in. A network entry that contains its own `version` is an error, since the file has one.
- **`add` validates the whole document before and after the edit,** including networks other than the one being changed, and refuses to write if any is invalid. It edits only the named network's contract and keeps the file's key order. The same hash may be added on different networks, since each network has its own list.
- **`createVersionGuard` takes one network's config.** Handing it the whole multi-network file produces the same "choose one" error as `loadConfig`.
- **Output.** Text output for an all-networks `check` has an `== name ==` heading per network. JSON is `{ ok, exitCode, networks: { name: report } }`. With `--network`, output is identical to a single-network check. `watch` lines and `add` output name the network when the file has several.
- **What is not built.** No single process watching several networks at once (run one `watch` per network), no per-network defaults inherited from the top level, and no environment-variable selection in the CLI itself (use `--network`).
- **Verification.** 70 new tests: 35 on the loader (every rule inside a network, aggregate error paths, selection rules, prototype-name lookups), 32 on `check`, `add` and `watch` with two fake chains, and 3 through the built binary. The 429 earlier tests passed unchanged after the library and CLI refactor. By hand against live testnet, with a `mainnet` section deliberately pointed at the testnet RPC: `check` exited 2 and reported `The RPC serves network "Test SDF Network ; September 2015" but the config expects "Public Global Stellar Network ; September 2015"` for that section while checking testnet normally; `check --network testnet` exited 0; `add` without `--network` refused and listed the networks; `add --network testnet` changed only testnet. Two test-helper bugs were found and fixed along the way (raw Wasm bytes being written as JSON, and a regex lost in a scripted edit).

## D-020: Stale is announced on time; timer limits (hardening, built on request)

- **Date:** 2026-10-08
- **The gap this closes.** D-011 and the docs said that a contract going `stale` through time alone is not pushed to subscribers. `isWritable()` was always correct, but a UI that only listens to `subscribe` could keep a write button enabled for up to about 0.55 times `maxStalenessMs` after the data went stale (the longest wait between failing polls), because it only heard at the next poll. That is now fixed and the limitation is removed from the docs.
- **How.** While the guard is running, one timer is armed for the soonest moment a supported contract's last success becomes more than `maxStalenessMs` old (`lastSuccessAt + maxStalenessMs + 1`; exactly at the limit is still fresh, as before). When it fires, subscribers are told and the timer is re-armed. It is re-armed after every poll and every fresh check, so a refresh pushes the deadline out. Only `supported` contracts matter: any other status blocks writes before and after.
- **Lifetime.** The timer exists from a successful `start()` until `stop()`. After `stop()` there are no announcements and no timers; the answers from `status()`, `isWritable()` and `health()` remain correct. A restart re-enables it. The timer is unref'd, so it never keeps a process alive, and listener errors are handled as for every other announcement.
- **Found while testing: a latent timer bug.** `setTimeout` cannot wait longer than 2^31-1 ms (about 24.8 days); a longer delay fires after a millisecond. The config allowed any `pollIntervalMs`, and a large `maxStalenessMs` could push the poller's backoff past the limit, so a misconfigured guard could have turned its poll timer into a tight loop against the RPC. Two fixes: poll delays are clamped to `MAX_TIMER_MS` in `nextDelayMs`, and the stale timer waits in steps for long limits; and `pollIntervalMs` is now limited to one day (`MAX_POLL_INTERVAL_MS`, 86,400,000), which is a validation change. Nothing in the spec asked for polling less than daily, and the default is 30 s. `maxStalenessMs` has no upper bound.
- **Verification.** 15 new tests with fake timers and the longest jitter, so that failing polls are as late as possible and cannot hide the timer: the announcement lands exactly 1 ms after the limit, once, with the recovery announced after it; it never fires while checks succeed; a fresh check moves the deadline; `stop()` leaves no timer and no announcement; a restart re-arms it; unref; a throwing listener; and a 40-day limit (longer than a timer can wait) announced at exactly the right millisecond. The same was run with real clocks against live testnet, with the RPC made to fail after the first good check and a 10 s limit: stale was announced 10,007 ms after the last good check, with writes already blocked. The 499 earlier tests passed unchanged.

## D-021: `wasmward init` (built on request; not in the spec or backlog)

- **Date:** 2026-10-08
- **Why.** Every new user starts by hand-writing JSON and finding a Wasm hash. `init` removes that step, and the live hash is available from the chain. The spec lists `hash`, `add` and `check` as the commands and did not ask for this one; it is small, additive and does not change any existing behaviour.
- **The trust decision is the whole design.** Starting from the code that is live today means accepting it as supported, on the RPC's word. A security tool should not do that silently, so: `--wasm <file>` is the recommended path and needs no network at all; the network path prints a warning to stderr on every run (suppressed in `--json` mode, where `source: "network"` carries the same fact); and the docs steer people to `--wasm` followed by `check`. The default when `--wasm` is absent is the network path, because a command that needs a file to do anything at all would be less useful for exploring a contract.
- **It only starts from something it can protect.** It verifies the network passphrase, then refuses and writes nothing for a missing contract, an expired instance, a Stellar Asset Contract (which Wasmward cannot verify), a failed lookup, an unreachable RPC and a wrong network. A fallback endpoint is not used: `init` talks to one endpoint it was told about.
- **Networks.** `--preset testnet` fills in the public RPC and the testnet passphrase. `--preset mainnet` fills in only the passphrase and demands `--rpc-url`, since there is no public mainnet RPC to point at, and a made-up default would be worse than none. `--rpc-url` may replace a preset's address; `--passphrase` that contradicts the preset is an error. Anything else takes `--rpc-url` and `--passphrase`. Preset names are looked up as own properties, so `constructor` is not a preset.
- **Validation before work.** The draft config is validated with a placeholder hash before any network call, so a typo in a name, a contract ID, an address or a label fails fast. The real config is validated again before it is written: nothing is written that would not load.
- **Never overwrites.** The target is checked first, before any network work. The file is written to a temporary file in the same folder and then hard-linked into place, which fails if the target exists, so two simultaneous runs cannot overwrite each other and a reader never sees half a file. Where the file system cannot make hard links, it falls back to an exclusive create (`wx`), which also refuses to overwrite.
- **Scope.** It writes the single-network format for one contract. Several contracts or networks are added by `add` and by editing the file. It has no `--force`.
- **Verification.** 38 new tests (35 in-process with a fake chain, 3 with a mocked file system for the link fallback and the race after the early check) and 2 through the built binary against a local fake RPC. By hand against live testnet: `init` from the chain produced the same hash as `init --wasm` on the local v1 build; `check` passed on the created file; a second `init` refused; and a contract ID that turned out to be a Stellar Asset Contract was refused with no file written. One test bug (an `await` inside a non-async callback) was caught by the type checker.

## D-022: Bugs found by reading the code back, and one still open

- **Date:** 2026-10-08
- **Why a review round.** A great deal of code had been added quickly, so this round re-read the core modules instead of adding a feature. Three real bugs were found and fixed, each with a regression test that was shown to fail without its fix (the fixes were stashed and the tests run: all 12 failed with the expected symptoms).
- **1. The stale timer spun (D-020).** Once a contract had been announced stale, its stored status stayed `supported` until the next poll, so `scheduleStaleCheck` computed a zero delay and re-armed itself in a loop for up to about half the staleness limit. Measured with real clocks: 414 timers in about 6 seconds. The fake-timer tests of D-020 missed it because fake timers turn a repeating zero delay into 1 ms steps, which stays under their loop limit. Fix: only contracts that are still fresh are waited on, and the minimum delay is 1 ms. The regression test asserts that no timer is armed in the quiet window after the announcement (2,000 were without the fix).
- **2. Retrying `start()` could bypass the wrong-network rule (D-018).** A primary on the wrong network throws `ConfigError`. The endpoint set remembered the rejection but replayed it as a plain `Error`, so a second `start()` read it as an outage, skipped the primary and could succeed through a fallback, against the spec. Fix: a remembered rejection is replayed as `ConfigError`.
- **3. An uppercase http scheme crashed.** The config check normalises case, so `HTTP://127.0.0.1:8000` was accepted, but the RPC clients were built with `url.startsWith('http://')`, so `allowHttp` was false and the SDK threw an "insecure server" error, from `createVersionGuard` and from every CLI command. Fix: `usesPlainHttp` asks the URL parser, and both places use it.
- **Also changed.** `WasmwardConfigInput` no longer requires `pollIntervalMs` and `maxStalenessMs`, which have defaults. The type was stricter than the file format; this loosens it.
- **Resolved in D-023: a hung RPC leaves its socket open.** The application-level timeout abandons a request but does not cancel it. The SDK's `rpc.Server` declares a `timeout` option, but in 17.2.1 nothing in `rpc/server.js` reads it, so it has no effect (confirmed: a server that never answers still held its socket 2.5 seconds after the timeout fired, with and without the option). During a long outage that means one dangling request per poll until the operating system gives up. It does not affect correctness: the guard still fails closed on time and the poller does not overlap ticks. A likely fix, not yet tried, is to set `server.httpClient.defaults.timeout`, which the SDK's fetch client does honour in its request config, or to send requests with an abort signal through the client's interceptors. This should be done and tested against a hung server before 0.1.0 is published.
- **Also noticed; fixed in D-017's follow-up below.** In the browser example, flipping the build selector twice quickly can leave the first guard running, because `begin()` is not serialised. It is harmless for a demo, but easy to fix with a generation counter.

## D-023: Requests to a hung RPC are really cancelled (closes the open item in D-022)

- **Date:** 2026-10-08
- **The problem.** The lookup timeout abandoned a request without cancelling it. `rpc.Server` declares a `timeout` option but never reads it in @stellar/stellar-sdk 17.2.1, so a request to an RPC that accepts connections and never answers stayed in flight indefinitely. In the guard that meant one dangling request per poll during an outage. In the CLI it was worse: the process stayed alive after printing its answer, so `wasmward check` in a deploy pipeline would **hang** on an unresponsive RPC instead of exiting with code 2.
- **The fix.** `createRpcClient(url, timeoutMs)` builds the `rpc.Server` and sets `httpClient.defaults.timeout` to `timeoutMs + CLIENT_ABORT_SLACK_MS` (1 s). `httpClient` is a documented public property of the SDK, and its fetch client turns that setting into an abort signal that cancels the request. The slack means the lookup's own message (`getLedgerEntries timed out after Nms`) is the one reported and the transport abort follows a second later, rather than the two racing. The guard and every CLI command use the factory, with the request timeout they already used (the smaller of the poll interval and 10 s). It is exported for people building their own clients. It also replaces two copies of the code that decided whether a URL needed `allowHttp`.
- **The idle connection is not a hang.** After an abort the HTTP client reopens an idle pooled connection, which closes by itself after its keep-alive timeout. The first version of the test counted open connections and failed on this. The tests now count requests still in flight, which is what matters.
- **It depends on an SDK internal.** The workaround relies on the fetch client reading `defaults.timeout`. A control test shows that the bare SDK client still leaves the request in flight, so it will fail when the SDK starts honouring `timeout`, which is the signal to remove the workaround.
- **Verification.** 6 new tests: the request is abandoned after the timeout and the lookup reports its own message; a network check is abandoned too; a merely slow response (200 ms against a 300 ms limit) is not cut off; the bare client control; the URL scheme cases; and a real-process test that `wasmward check` against a silent server exits with code 2 and the timeout message. The real-process test was run with the fix stashed: the CLI never exited and the test hit its 60 s limit; with the fix it finishes in about 6 s.

## D-024: The browser example no longer leaks guards when the selector changes quickly (follow-up to D-017 and D-022)

- **Date:** 2026-10-08
- **The bug.** Changing the "which build of the app" selector several times quickly started several `begin()` calls at once. Each stopped the guard it saw, then created a new one, so only the newest guard was referenced and the others kept polling the RPC for as long as the page stayed open.
- **Reproduced in a real browser first** by wrapping `fetch` to count `getLedgerEntries` calls and changing the selector three times in a row: three guards polled in parallel, **9 requests in 30 s** where one guard makes 3.
- **The fix** (in `Wasmward-frontend/src/main.js`): every choice takes a number, and only the newest may keep a guard. An older `begin()` that wakes up after a newer one has started returns without creating anything; a guard that finishes starting after being replaced stops itself; a replaced guard's subscriber no longer touches the page; and the deposit button is disabled the moment a switch begins, so it cannot be clicked with no guard behind it.
- **Verified in the same real browser after the fix:** the same three quick changes produce **3 requests in 30 s** (one guard, polling about every 11 s), the page ends in the state of the last choice (`older`, `unsupported`, button disabled), and switching back gives `supported`, an enabled button and a working demo deposit. About two requests per 15 s on a settled page, and no other hosts contacted.
- **Not understood:** one `net::ERR_NAME_NOT_RESOLVED` console error appeared during this session. The page's resource timing shows requests only to its own server and the testnet RPC, so it was not requested by the page; it is most likely from the browser pane itself. Earlier sessions with this page showed no console errors.

## D-025: The packed package is tested the way consumers will use it

- **Date:** 2026-10-08
- **The gap.** Until now the package had been checked only by `npm pack --dry-run` (its file list), by ESM imports and by running the CLI. The CommonJS build had never been loaded and no TypeScript project had ever resolved the type declarations, even though `exports` has separate `import` and `require` branches with their own `.d.ts` and `.d.cts`. A mistake there would only have appeared after publishing, for a user.
- **The test** (`test/unit/consumer.test.ts`). It runs `npm pack`, unpacks the tarball into a throwaway project's `node_modules/@wasmward/core`, and uses it the way a user would:
  - `import` from an `.mjs` file, and `require` from a `.cjs` file, each checking that the expected functions and classes exist (including the `/node` entry) and that `loadConfig`, a default, `createVersionGuard` and `hashWasm` (against the SHA-256 of "abc") give the right answers;
  - TypeScript, strict, under `module: node16` and `moduleResolution: node16`, from both an ES module file (`.mts`) and a CommonJS file (`.cts`). The sources use real types and also contain `@ts-expect-error` lines for wrong calls (a number where a string is needed, an unknown option). If the declarations ever resolved to `any`, those lines would stop being errors and the compile would fail, so a pass means the types are real;
  - the installed CLI, and a check that the installed folder holds only `LICENSE`, `README.md`, `dist` and `package.json`.
- **Offline and fast.** The peer dependencies (`@stellar/stellar-sdk`, `zod`) resolve by walking up to this repository's `node_modules`, so nothing is downloaded. The throwaway folder lives inside the repository (git-ignored, ignored by ESLint) so that resolution works, and is removed afterwards; a folder that is briefly locked by an indexer does not fail the run.
- **No external `tar`.** The first version shelled out to `tar` and failed in this environment (`unexpected end of file`), so the tarball is unpacked by a small reader written in Node (gunzip, then ustar headers). That also removes a dependency on whichever `tar` is on the PATH.
- **What it found.** Nothing wrong with the package: it passed once the test's own mistakes were fixed (a listener that returned a value, `@ts-expect-error` comments above a multi-line call where TypeScript reports the error on the last line, and the 5-second default timeout, since loading the SDK takes several seconds on this machine). That is a result: the `exports` map, the CommonJS build and both sets of declarations work.
- **Does it catch breakage?** Yes for a broken entry: with the CommonJS entry pointed at a missing file, the `require` case failed. A wrong `types` path alone is not caught, and cannot be: TypeScript falls back to the declaration file next to the `.cjs`, so consumers are not affected either.
- **In CI.** It runs in the normal test job (the build happens first), alongside the existing `npx`-from-tarball step.

## D-026: A threat model, written from the code

- **Date:** 2026-10-08
- **Why.** For a security tool, the question a user or reviewer asks first is what it does and does not protect against, and the answer was spread across the README, the operations guide, SECURITY.md and many decision records. `docs/THREAT-MODEL.md` states it once: the exact guarantee, what is defended (each row pointing at the mechanism and, where there is one, the decision record), what is trusted rather than defended, what cannot be done, the failure behaviour as a table, and how each claim is checked.
- **Each claim was checked against the code before it was written.** The library calls only `getNetwork` and `getLedgerEntries`, so everything rests on those two answers. It never reads the contract's separate code ledger entry, so a contract whose instance is live but whose code entry has expired is reported `supported`; calls to it fail rather than misbehave, so that costs availability, not safety, and it is listed as a limit. Plain `http` is limited to `localhost` and `127.0.0.1`. A backwards or non-numeric clock is `stale`. Simulation is an RPC call to the same endpoint, so it adds no independence from a lying RPC.
- **Honest about trust.** The most important sentences are the ones about assumptions: the RPC is believed (the passphrase check proves a claim, not authenticity), every listed endpoint is trusted equally, the config's author decides what is supported, a hash on the list is a promise by the owner, and a browser can be tampered with. None of these was new, but none was written down in one place.
- **Timing stated as measured.** The upgrade-detection figures are those actually observed (0.7 to 0.8 s locally, 3.8 s on a hosted runner, with a 5 s poll interval) and the document says the bound is one interval plus jitter rather than a fixed delay.
- **A tooling slip, caught.** While preparing the file, a `sed` command with a backtick in its pattern matched the empty string and put a stray backtick at the start of every line. It was caught because the next read-back looked wrong, repaired by stripping exactly that character, and the result was then checked for structure (headings, 25 table rows, balanced code spans on every line) and read in full before committing.

## D-027: Show how long an instance has left (closes part of a limit in D-026)

- **Date:** 2026-10-08
- **Why.** The threat model listed "cannot warn that an instance is about to expire" as a limit. The lookup already returns the instance's expiry ledger and the latest ledger, and they were being discarded after deciding whether the instance was archived. Keeping them costs nothing, and an instance that expires breaks writes with no earlier sign.
- **What.** `ContractState` gains `liveUntilLedger` and `latestLedger` (set by a lookup that found an instance, replaced by the next one, cleared when no instance was found, kept across errors so the last known value stays visible). `ledgersUntilExpiry(state)` is their difference, never below zero. The health report gains `ledgersUntilExpiry`. `wasmward check` appends `(expires in about N days)` to a supported contract, and adds `; extend its lifetime soon` under `EXPIRY_WARNING_LEDGERS` (120,960 ledgers, about 7 days).
- **Informational only, deliberately.** It does not change a status, block a write or alter an exit code. There is no authoritative "too close" figure to enforce, a deploy gate that fails on a contract that is simply due for maintenance would be a nuisance, and the guarantee in the threat model stays exactly as small and as testable as it was. People who want a gate can compare `ledgersUntilExpiry` in the JSON with their own number.
- **Rough on purpose.** A ledger is taken as 5 seconds, so the wording is "about N days" or "about N hours", and the value is a snapshot from the last check, not a countdown. The first version of the notes would otherwise have implied precision the network does not offer.
- **Still not covered.** Only the instance is reported. The contract's code is a separate ledger entry with its own lifetime that Wasmward never reads, which the threat model keeps as a limit and the operations guide tells people to extend as well.
- **It found a real problem straight away.** Run against the live testnet fixture, which the README example and the browser demo both point at, it said "expires in about 6 days; extend its lifetime soon" (104,492 ledgers, matching the roughly seven-day lifetime it was deployed with a day earlier). The fixture would have expired within a week and broken both public demos without warning.
- **Fixture extended, and a script added.** `Wasmward-contract/scripts/extend.sh` extends the instance and the code of both builds (about 29 days by default), with its README explaining why. It was run once: `check` then said "expires in about 29 days" with no warning. It handles no secret directly; it uses the identity `deploy.sh` created.
- **Verification.** 21 new tests: state (replaced, kept on error, cleared, never below zero, unknown), the wording table including its boundaries (719 and 720 ledgers, 34,559 and 34,560, and the 7-day constant), the `check` output including the exact threshold (120,960 against 120,959), that a near-expiry contract is still `supported` with exit 0, that unsupported contracts show no note, and the JSON field being present or absent. The 577 earlier tests passed apart from exact-shape assertions that now include the new fields. No new dependency.

## D-028: An opt-in expiry gate, used by a scheduled fixture check (spans all three repositories)

- **Date:** 2026-10-08
- **Why.** D-027 made the time left visible but deliberately informational. That left a hole: the fixture the README example and demo depend on nearly expired unnoticed. A check that only runs when someone deploys cannot catch something that happens between deploys. The fix is a way to make "too close" fail, used on a schedule, and nothing else about `check` changes.
- **Backend: `wasmward check --min-ttl-days <n>`.** Opt-in; without it every output and exit code is identical to before (all 598 earlier tests passed unchanged). A *supported* contract with fewer than n days left makes the check exit 1. It reuses exit 1 ("not OK for a gate") instead of inventing a code, since a script cares that it is non-zero and the output says which kind. The comparison is in ledgers (n x 86,400 / 5, rounded up) and is exclusive: exactly the minimum passes, one ledger fewer fails; both edges are tested, including half a day. Values that are not a finite number between 0 and 36,500 days are an input error (exit 2) before any network work, and the flag is refused for commands it does not apply to rather than ignored. In JSON the contract gets `belowMinTtl: true`, the report gets `minTtlDays`, and `ok` is false whenever the exit code is 1 for this reason, so the two cannot disagree. A contract that already fails (unsupported, missing and so on) is not flagged a second time, and a failed lookup stays exit 2. A multi-network check applies the minimum to every network.
- **Contract repository: a weekly workflow that uses Wasmward on itself.** `fixture.wasmward.json` (public values only: the live fixture's contract ID and the hashes of both builds) and `.github/workflows/fixture-health.yml`, which runs every Monday, builds Wasmward from its repository (it is not on npm yet) and runs `check --min-ttl-days 3`. A red run means the fixture is missing, unsupported, unreachable or about to expire, and the run's last step prints what to do (`scripts/extend.sh`, or `scripts/deploy.sh` if it has gone). This is the project using its own tool on its own dependency. It also adds the first CI that repository has had (below).
- **Contract repository: CI.** The crate had tests but no workflow. `.github/workflows/ci.yml` runs `cargo fmt --check`, `clippy -D warnings` and the tests for both the v1 and v2 builds, then builds both Wasm variants and fails if their hashes are equal, since the whole point of the fixture is that they differ. Each command was run locally first and passes. One observation from doing so: a plain `cargo build` and the `stellar contract build` that produced the deployed fixture give different hashes for the same source, another reason the operations guide says to hash the artifact that was deployed.
- **Frontend: the demo shows the time left.** A "Time left" row uses the library's own `ledgersUntilExpiry` and `describeTimeLeft`, and turns amber with "extend its lifetime soon" under `EXPIRY_WARNING_LEDGERS`. Verified in a real browser against live testnet ("about 29 days", normal style), and, since live data cannot show the warning, with the RPC answer intercepted in the page to give about 7 hours left: the row turned amber and read "about 7 hours: extend its lifetime soon", with the status and button behaving as before. The browser console showed resource errors (`ERR_NAME_NOT_RESOLVED`, `ERR_CONNECTION_CLOSED`); an identical list appeared on a bare text page with none of this code, so they are not from the demo, but whether that buffer is cumulative or pane-level is not known.
- **Verification (backend).** 28 tests in `test/unit/cli-expiry.test.ts` for the expiry output and this flag: pass and fail cases, both exact boundaries, fractions, unchanged behaviour without the flag, the JSON markings, no double flagging, exit 2 precedence, eight invalid values (`abc`, `0`, `-1`, empty, a space, `40000`, `Infinity`, `NaN`), refusal for other commands, the usage text, and two networks with one expiring. The live fixture passed at 3 days and failed correctly at 40 (it has about 29).

## D-029: A reusable GitHub Action, adopted by the other two repositories (spans all three)

- **Date:** 2026-10-08
- **Why.** The contract repository's weekly health check had to copy a block of steps (check out Wasmward, set up pnpm and Node, install, build, run the command) just to use the tool, and any other project would have copied the same block. The way most people will use Wasmward in a pipeline is "fail my workflow if the contract is wrong"; that should be one step.
- **Backend: `action.yml` at the repository root,** used as `contract-version/Wasmward-backend@<ref>`. A composite action: it sets up Node 22, builds Wasmward from the repository it lives in (it is not on npm yet, so about a minute), and runs `wasmward check` with three inputs: `config` (default `wasmward.json`), `network` and `min-ttl-days` (both empty by default). The step's result is the command's exit code (0, 1 or 2 as documented), and the output is also written to the job summary.
- **Inputs never become shell.** A workflow input interpolated into a script is a classic injection route (a value can contain `; command`). Here the three inputs reach the shell only as environment variables, are expanded in double quotes, and the optional flags are added only when set. `test/unit/action.test.ts` enforces this: every use of `${{ inputs.* }}` must be an `env:` entry (shown to fail when one was put into the script text instead), and no `$WASMWARD_*` expansion in the command may be unquoted. The test also checks the action is composite, declares exactly the inputs the CLI has options for (all optional), passes the exit code through, writes the summary, uses only flags the CLI accepts, and is documented in the README. The action's real behaviour is exercised by the workflows that use it.
- **Contract repository.** `fixture-health.yml` now is the action call plus the "what to do" hint on failure, instead of about thirty lines of setup. A manual run passed against live testnet.
- **Frontend.** `wasmward.json` describes the demo's contract (the same contract and hash `src/main.js` builds in code), and CI gained two things: an offline step that fails if `src/main.js` and `wasmward.json` name different contracts or hashes (shown to catch a deliberately changed hash), and a separate `contract-alive` job that runs the action with `min-ttl-days: 1`. It is a separate job so that a testnet outage, or a contract that is about to expire, turns CI red without hiding whether the demo builds. A demo that points at a dead contract passes every code check and is still broken; this is the check that notices.
- **Observed on GitHub.** Both repositories ran the action successfully against live testnet and printed `vault supported (v1) ... (expires in about 29 days)` and `1 of 1 contracts supported with at least 1 day left` (and 3 days in the contract repository).
- **Known limits.**
  - `@main` moves. The README says to pin a commit or tag once a version should not change underneath you; there is no release tag yet.
  - Building from source costs about a minute per run until the package is published, at which point the action can install it instead.
  - The two repositories' CI now depends on testnet being up: the frontend isolates that in its own job, and the contract's health workflow is meant to fail when the fixture is unreachable.
- **Verification.** 8 new tests. Backend commits were split, so the run for the tests commit was red for one commit: the README assertion fired before the documentation commit that follows it; the next commit is green.
